# 05 · 排错手册

先区分“没有收到事件”“模型没完成”“QQ没发成功”，不要一上来更换Key或开放全部端口。

## 1. 完全不回复

依次检查：

1. `systemctl is-active qq-deepseek qq-napcat`。
2. `curl -fsS http://127.0.0.1:8765/health`，只说明业务HTTP可用。
3. `sudo python3 scripts/check.py`，确认QQ登录身份与配置匹配。
4. 私聊账号在`allowed_private_users`，群在`allowed_groups`且机器人确实在群。
5. 群内先用@测试，不把随机12%接话当作每句必回。
6. OneBot反向HTTP启用、URL是`http://127.0.0.1:8765/event`、array格式、两端Token一致。
7. 看业务日志的eligible标记与失败类别。

同一用户正在生成或分条回复时，当前实现可能忽略其紧接着发来的新事件；先等本轮结束再试。并发槽和每日额度也会限制触发。本项目当前没有无限消息队列。

## 2. 回调401

NapCat HTTP客户端使用`x-signature`。程序对原始请求体使用共享Token做HMAC-SHA1验签，不是只检查Bearer头。核对当前运行的bot.py与仓库一致；不要使用早期不支持该验签的旧脚本。

不要把Token贴到Issue。可在本地对比配置而不输出完整凭据。

## 3. 回调413或请求体读不到

真实网关可能使用`Transfer-Encoding: chunked`。当前入口支持受大小限制的分块读取；若仍运行固定Content-Length旧代码，替换为仓库版本并重启。不要通过无限提高请求体上限处理版本不匹配。

## 4. Key/模型/余额错误

- 401：凭据或认证问题，重新在服务器隐藏输入正确Key。
- 402或账户不可用：在官方平台检查余额/账户状态。
- 400：模型名、思考参数、工具调用结构等请求格式不匹配。
- 429/5xx：服务限流或暂时不可用，稍后再试，不连续轰炸。

当前某些模型请求失败只记录日志，未必能向QQ发出错误说明；不要将“无回复”直接判断为账号掉线。

## 5. 深度思考明显变慢

思考模式的8192预算包含模型思考消耗；请求超时180秒。发送前的人为等待发生在答案准备好之后。用`/深度思考 关闭`恢复普通模式。默认关闭。

思考+联网采用先普通模式选择搜索、再单独思考作答，因此可能有两次模型请求。不要把推理过程加入群消息或导出到公开日志。

## 6. QQ登录/二维码问题

二维码只在有效期内可用，过期就重新获取。重启后不自动登录时，检查HOME、运行用户和QQ数据目录是否统一。被踢下线、官方设备确认、验证或账号限制需按QQ官方流程处理，不通过本项目绕过。

## 7. 表情包不发送

每次最多一个，通常至少三次聊天才配一次；明确请求可提前，但仍有90秒冷却。检查图片在`memes/`目录内、catalog键正确、QQ进程能读取路径。不要使用任意外部图片地址代替白名单。

## 8. 空间接口失败

QQ能聊天不代表空间操作一定可用。需要账号空间可用、网关版本支持对应接口，且`owner_qq`私聊授权正确。

已验证的列表调用是`get_qzone_msg_list`搭配`format:native,target_uin`。部分兼容调用会出现“响应不完整”，原生模式不接受`page_num`、`num`等兼容分页参数。当前只显示服务端原生页前5条。

写入超时并不证明没发出去。程序不会自动重发相同内容；先到QQ空间核对。只有拿到说说tid才显示发布成功。

## 9. 系统/端口问题

```bash
sudo ss -lntp
sudo journalctl -u qq-deepseek -n 60 --no-pager
sudo journalctl -u qq-napcat -n 60 --no-pager
```

3000是OneBot API、6099是WebUI、8765是业务回调。它们在同机运行时不需要对公网开放。若端口被占用，查清哪个实例占用，避免启动第二个QQ网关。

## 提交问题时

提供系统版本、Python版本、NapCat/QQ版本、执行到哪一步、脱敏后的错误类别、是否收到事件，以及离线测试结果。删除Key、Token、二维码、QQ登录数据、个人账单和聊天正文。
